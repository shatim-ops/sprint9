# Задание 2. Сервис отчётов

Схема: `BionicPRO_C4_reports_to-be.drawio` (рядом png-экспорт). Добавленное в
этом задании обведено оранжевым. Контур SSO показан свёрнуто, подробности в Task1.

## Поток данных

1. Airflow раз в сутки (01:00 UTC) запускает DAG `bionicpro_reports_mart`.
2. Из CRM забирается срез "протез, владелец, модель". ФИО, телефон, email и дата
   рождения в OLAP не копируются: отчёту они не нужны, а после утечки плодить
   копии персональных данных незачем. Пользователь в витрине это логин.
3. Из PostgreSQL с телеметрией забираются события за ещё не обработанные сутки
   плюс два последних дня. Протез работает через 4G и может дослать данные
   позже, поэтому хвост каждый раз пересчитывается. Читается серверным курсором
   пачками по 50 тысяч строк, чтобы не держать всё в памяти и не вешать
   долгий тяжёлый запрос на боевую базу.
4. Агрегация считается уже в ClickHouse, результат пишется в витрину
   `reports.user_prosthesis_daily`.
5. В `reports.etl_loads` пишется, по какую дату включительно витрина готова.
6. Сервис отчётов по запросу читает готовые строки витрины. Расчётов в момент
   запроса нет, только суммирование дневных строк в итог по периоду.

На стенде CRM изображает PostgreSQL с двумя таблицами (`crm_db/init.sql`), на
схеме оставлен Oracle из исходной диаграммы. Для DAG разница только в
подключении. Телеметрия в `telemetry_db/init.sql` синтетическая и генерируется
за последние 10 дней от момента первого запуска, так что стенд не устаревает.

## Витрина

`clickhouse/init/01_schema.sql`

- Гранулярность: пользователь, протез, день. Метрики: число движений, число
  нераспознанных, среднее, p95 и максимум времени реакции, сколько откликов
  медленнее 100 мс (порог из описания кейса), активные часы, минимум и среднее
  заряда, шум сигнала, самое частое движение.
- `ORDER BY (user_login, prosthesis_id, report_date)`. Отчёт всегда читается по
  одному пользователю, и с таким ключом ClickHouse поднимает несколько гранул,
  а не сканирует таблицу. Это и есть "быстрый доступ по пользователю".
- `ReplacingMergeTree(loaded_at)`: повторная загрузка того же дня не даёт
  дублей, читаем с `FINAL`. На выборке по одному пользователю это дёшево.
- Партиции по месяцам. По дням было бы удобнее перезаливать, но за несколько
  лет наберётся больше тысячи партиций, для ClickHouse это уже плохо.
- Сырые события `telemetry_events` партиционированы по дням, перезаливка дня
  это `DROP PARTITION` и `INSERT`. TTL 35 дней, история в сыром виде в OLAP не
  копится.
- У сервиса отчётов свой пользователь `reports_api` с `SELECT` на витрину и
  журнал загрузок, писать он не может.

## DAG

`airflow/dags/bionicpro_reports_mart.py`

```
resolve_window -> load_telemetry -> build_mart -> register_load
load_crm -> build_mart
```

- Расписание `0 1 * * *`, `catchup=False`, `max_active_runs=1`.
- Окно загрузки считается от журнала `etl_loads`, а не только от интервала
  запуска. Первый запуск поднимает всю историю, которая есть в источнике,
  следующие догружают новые сутки. Если DAG пару дней не работал, следующий
  запуск сам закроет пропуск, backfill не нужен.
- Грузятся только полные сутки, сегодняшний день в витрину не попадает.
- Все шаги идемпотентны, DAG можно перезапускать руками сколько угодно.
- Подключения заданы переменными `AIRFLOW_CONN_*` в `docker-compose.yaml`.

## API

`reports-api`, FastAPI.

| Метод | Что делает |
|---|---|
| `GET /reports?date_from=&date_to=` | Отчёт текущего пользователя. Без периода отдаёт последние 7 обработанных дней |
| `GET /reports/{user_login}` | То же с логином в пути. Чужой логин даёт 403 ещё до обращения к базе |
| `GET /health` | Для проверки живости |

Доступ:

- Без токена, с просроченным токеном, с чужой подписью, с чужим issuer или
  токеном другого клиента (`azp`) будет 401. Подпись проверяется по JWKS Keycloak.
- Без роли `prothetic_user` будет 403.
- Чей отчёт отдавать, берётся из `preferred_username` токена. Параметра
  "пользователь" у основного эндпоинта нет вообще, так что запросить чужой
  отчёт нечем. На стенде связка с CRM идёт по логину. В проде я бы хранил в
  CRM `sub` из Keycloak: логин можно сменить, `sub` нет.

Период и необработанные данные:

- API читает из `etl_loads`, по какую дату витрина готова, и правую границу
  периода обрезает по ней. В ответе есть `period.processed_until` и флаг
  `period.truncated`, UI по нему показывает предупреждение.
- Если запрошенный период целиком позже обработанной даты, ответ 404 с текстом,
  по какое число отчёты доступны. Если DAG ещё ни разу не отработал, тоже 404.
- Если у пользователя за период нет данных (например, сбор телеметрии
  отключён), 404 с отдельным сообщением.

Тесты на авторизацию и работу с периодом лежат в `reports-api/tests`, ClickHouse
в них заменён заглушкой:

```bash
cd reports-api
pip install -r requirements-dev.txt
python -m pytest -q
```

## Как проверял

Весь путь целиком: логин через Keycloak с PKCE, запуск DAG, запрос отчёта из UI.

| Сценарий | Результат |
|---|---|
| первый запуск DAG | окно от первого события до вчера, события загружены, в витрине строка на пользователя, протез и день |
| повторный запуск DAG | окно два последних дня, в витрине после `FINAL` то же число строк, дублей нет |
| `/reports` без токена | 401 |
| `/reports` под `user1` | 403 |
| `/reports` под `prothetic1` | 200, два протеза, 7 дней |
| `/reports/prothetic2` под `prothetic1` | 403 |
| `/reports?date_from=<сегодня>` | 404, "Отчёты доступны по <вчера> включительно" |
| `/reports?date_to=<через неделю>` | 200, период обрезан, `truncated: true` |
| `/reports` под `prothetic3` | 404, данных о работе протеза нет |

Проверить содержимое витрины напрямую:

```bash
docker compose exec clickhouse clickhouse-client -u reports_etl --password reports_etl_password \
  -q "SELECT user_login, prosthesis_id, report_date, movements_total, avg_response_ms FROM reports.user_prosthesis_daily FINAL ORDER BY 1, 2, 3"
docker compose exec clickhouse clickhouse-client -u reports_etl --password reports_etl_password \
  -q "SELECT * FROM reports.etl_loads ORDER BY finished_at"
```
