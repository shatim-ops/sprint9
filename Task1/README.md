# Задание 1. Повышение безопасности системы

## 1.1 Архитектура управления учётными данными

Схема: `BionicPRO_C4_auth_to-be.drawio` (рядом png-экспорт). За основу взята
исходная диаграмма контейнеров, новое и изменённое обведено оранжевым.

### Что именно сломалось

Public client в браузере с обычным Code Grant: код авторизации можно
перехватить и обменять на токены, потому что обмен ничем не привязан к тому,
кто начинал логин. Плюс токены Keycloak лежат в JS-контексте страницы, любая
XSS отдаёт их целиком, включая refresh. Поэтому решение из двух частей: PKCE
закрывает перехват кода (задача 1.2, сделано в коде), BFF убирает токены из
браузера (целевая архитектура на схеме).

### Требование 1. Учётные записи из источника в стране представительства

- В каждой стране свой каталог учётных записей (OpenLDAP, в репозитории уже
  есть заготовка в `ldap/`). Он остаётся источником правды по пользователям
  этой страны.
- Keycloak подключается к каталогу через User Federation, импорт пользователей
  выключен: пароль проверяется bind-ом в LDAP, атрибуты читаются по запросу, в
  базе Keycloak пользователи не оседают. В Keycloak DB остаются клиенты, роли,
  настройки realm и связи с внешними IdP, персональных данных там нет.
- На страну заводится отдельный realm. У realm свой каталог, свои внешние IdP,
  своя парольная политика и MFA. Требования регуляторов разные, и так их не
  приходится сводить к общему знаменателю.
- CRM, базы, API и каталог образуют "контур страны". При выходе в новую страну
  разворачивается такой же контур, общими остаются только Keycloak и BFF.
  Медицинские данные и ПДн из страны не уезжают.
- В токены кладём минимум: `sub`, роли, страна. ФИО, email и прочее API берёт
  из базы своей страны. Тогда даже утёкший токен персональных данных не несёт,
  а общий контур SSO не становится местом их обработки.

### Требование 2. Токены IdP не попадают на фронтенд

- Появляется `bionicpro-auth`, он же BFF. Это confidential client Keycloak с
  секретом, и Code Grant + PKCE выполняет он, а не браузер.
- Access- и refresh-токены BFF хранит в Redis в зашифрованном виде, ключ записи
  это идентификатор сессии. Клиенту уходит только непрозрачный session id: вебу
  в cookie с `HttpOnly`, `Secure`, `SameSite=Strict`, мобильному приложению в
  защищённое хранилище устройства.
- Запросы к API идут через BFF: он по сессии достаёт access-токен, при
  необходимости обновляет его и подставляет в заголовок. API токен проверяет
  как раньше: подпись по JWKS, issuer, роли.
- Refresh-токены ротируются (в Keycloak Revoke Refresh Token, повторное
  использование старого гасит сессию). Session id меняется после логина, чтобы
  не было фиксации сессии. У записи в Redis TTL не больше времени жизни
  SSO-сессии.
- Для запросов, меняющих состояние, нужен CSRF-токен. `SameSite` это первая
  линия, но не единственная.

### Требование 3. Внешние удостоверяющие службы разных стран

Identity Brokering в Keycloak. В российском realm это Яндекс ID и Госуслуги, в
других странах Google, Apple или национальные eID. Приложения про это ничего не
знают, для них IdP один. Роли внешний IdP не назначает: после первого входа
учётка связывается с записью в каталоге страны, и роли берутся оттуда.

### От чего отказался

- Один общий realm и один общий каталог на все страны. Проще, но тогда учётные
  данные всех стран лежат в одном месте, и первое же требование о локализации
  ломает схему.
- Свой Keycloak в каждой стране. Локализация идеальная, но SSO между странами и
  единая точка для BFF пропадают, а сопровождать приходится N инсталляций.
  К этому варианту можно вернуться, если какой-то регулятор запретит проверку
  учётных данных сервисом из-за границы.
- Оставить токены в браузере, но в памяти, а не в storage. От XSS не спасает.

## 1.2 PKCE

Что изменено:

- `frontend/src/App.tsx`: в `initOptions` добавлен `pkceMethod: 'S256'`.
  keycloak-js сам генерирует `code_verifier`, в authorization request уходит
  `code_challenge`, при обмене кода на токен уходит `code_verifier`.
- `keycloak/realm-export.json`, клиент `reports-frontend`: атрибут
  `pkce.code.challenge.method = S256`. Без него PKCE был бы необязательным, и
  атакующий мог бы просто начать поток без challenge. Заодно явно включён только
  standard flow, implicit и direct access grants выключены: password grant
  публичному клиенту не нужен, а поверхность атаки увеличивает.

Как проверял (Keycloak 21.1 с этим realm):

| Сценарий | Результат |
|---|---|
| authorization request без `code_challenge` | редирект с `error=invalid_request`, `Missing parameter: code_challenge_method` |
| обмен кода без `code_verifier` | 400 `invalid_grant`, `PKCE code verifier not specified` |
| обмен кода с чужим `code_verifier` | 400 `invalid_grant`, `PKCE verification failed` |
| штатный логин через фронтенд | в запросе на `/auth` есть `code_challenge_method=S256`, в запросе на `/token` есть `code_verifier`, токены выданы |
| password grant для `reports-frontend` | 400 `unauthorized_client` |

В браузере это видно в DevTools на вкладке Network: запрос `auth?...` с
параметрами challenge и POST на `token` с verifier.

BFF в коде этого спринта не реализован, по заданию в код идёт только PKCE.
Фронтенд стенда пока работает с Keycloak напрямую, на схеме показано целевое
состояние.
